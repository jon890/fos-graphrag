## ADR-018: 테스트에서 컨테이너를 띄우지 않는다. 서버는 JUnit 안의 Neo4j 로, 화면은 서버가 남긴 응답 스냅샷을 주는 가짜 API 로 테스트한다

- **status**: `accepted`
- **결정**: 자동 테스트는 Docker 없이 돈다(사용자 결정 2026-10-26).
  서버 통합 테스트는 Neo4j 5.26 을 `org.neo4j.test:neo4j-harness` 로 테스트 JVM 안에 띄우고, 가짜 OIDC 공급자는 `no.nav.security:mock-oauth2-server` 라이브러리로 같은 JVM 안에 띄운다.
  화면 테스트(Playwright)는 Vite 개발 서버를 띄우고 `page.route` 로 가짜 API 응답을 준다. 가짜 API 의 응답은 서버 JUnit 테스트가 실제 응답을 정규화해 남긴 JSON 스냅샷(`web/e2e/fixtures/`)이다.
  서버 동작에만 기대는 검사(저장 뒤 다른 사용자에게 보이는가, 권한, 동시 수정)는 서버 JUnit 테스트가 맡는다.
- **맥락**: 서버 테스트는 Testcontainers 로 Neo4j 와 가짜 OIDC 컨테이너를 띄웠고, 브라우저 테스트는 Compose 로 앱 이미지를 빌드해 띄운 뒤 돌았다.
  이미지 빌드와 스택 기동이 무거워 구현 단계마다 브라우저 테스트를 돌리지 못했고, Docker VM 디스크가 가득 찬 적이 있다. 앞 작업이 남긴 볼륨을 재사용해 브라우저 테스트가 거짓으로 실패한 적도 있다(PR #23).
  Neo4j 5.26 서버는 Netty 4.1 을, 앱의 Neo4j Java Driver 6.1 은 Netty 4.2 를 쓴다. 한 클래스로더에 두면 Neo4j 가 내부 채널을 열지 못한다(`IoHandle of type LocalServerChannel$LocalServerUnsafe not supported`, 2026-10-26 실측).
  그래서 하네스는 Spring Boot BOM 을 받지 않는 별도 Gradle 설정으로 받고, 테스트가 그 jar 들만 담은 클래스로더에서 띄운다.
- **대안 기각**:

  | 대안 | 기각 이유 |
  | --- | --- |
  | Testcontainers 를 두고 컨테이너를 재사용한다(`reuse`) | Docker 와 VM 디스크에 계속 기댄다. 재사용한 컨테이너에 앞 실행의 데이터가 남아 거짓 실패가 나는 문제는 그대로다 |
  | Compose 로 띄운 브라우저 테스트를 유지한다 | 이미지 빌드와 스택 기동이 단계마다 돌리기에 무겁다. 화면 테스트가 서버 상태를 공유해 시나리오를 순서대로만 돌릴 수 있다 |
  | 서버를 메모리 가짜 저장소로 테스트한다 | Cypher, 트랜잭션 시간 제한, 쓰기 잠금, 동시성을 확인할 수 없다. 운영과 다른 저장소를 하나 더 유지해야 한다 |
  | 하네스를 앱과 같은 클래스로더에 두고 Netty 버전을 맞춘다 | 서버(4.1)와 드라이버(4.2)가 서로 다른 Netty 메이저를 요구해 한쪽이 깨진다 |
  | Neo4j 2025 이후 버전의 하네스를 쓴다 | 운영(5.26 LTS)과 다른 서버로 테스트하게 된다 |
  | 화면 테스트의 가짜 API 응답을 직접 쓴다 | 서버 응답 모양이 바뀌어도 가짜 응답은 그대로라 화면 테스트가 낡은 계약으로 통과한다 |

- **결과**:
  - 얻는 것: 서버, 웹 단위, 화면 테스트를 Docker 없이 단계마다 돌린다. 화면 테스트는 서로 상태를 공유하지 않아 순서에 기대지 않는다. 서버 응답 모양이 바뀌면 스냅샷 파일의 diff 로 리뷰에 드러난다.
  - 감당할 것: 화면 테스트는 실제 서버를 거치지 않는다. 보안 헤더와 CSP, 세션 쿠키, 실제 OIDC 리다이렉트, 이미지 안의 정적 파일 제공은 서버 JUnit 테스트와 배포 뒤 운영 확인(`scripts/smoke-prod.ts`)이 맡는다.
    가짜 API 는 스냅샷에 없는 요청을 실패로 돌려 빠진 계약을 드러낸다. 스냅샷은 서버 테스트가 다시 만들고, 갱신한 파일을 함께 커밋해야 한다.
    운영 이미지와 Compose 설정은 자동 테스트로 띄워 보지 않는다. `scripts/tests/test_scripts.sh` 의 Compose 설정 검사와 배포 뒤 확인이 맡는다.
- **적용 범위**: 테스트 배치와 의존성 충돌 해결은 [코드 구조](../code-architecture.md) 의 「테스트」, 운영 확인은 [배포 문서](../deployment.md) 의 「배포 뒤 확인」 이 소유한다.
