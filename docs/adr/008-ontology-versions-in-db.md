## ADR-008: 온톨로지를 DB 에 버전으로 쌓고 ADMIN 이 웹에서 편집한다

- **status**: `accepted`
- **결정**: 온톨로지의 편집할 수 있는 부분(Claim 을 뺀 노드 타입, 관계 종류, 주장 종류)은 Neo4j 의 `:OntologyVersion` 에 버전으로 쌓는다. 저장할 때마다 전체 정의를 새 버전으로 남기고, API 는 저장한 순간부터 최신 버전으로 쓰기를 검증한다. ADMIN 만 웹의 폼 편집기와 YAML 편집기로 고친다. 서버 코드와 맞물린 부분(검토 상태, 변경 이력의 작업과 항목 이름, Claim 관계, Claim 타입)은 지금처럼 저장소의 YAML 이 소유하고, 시작할 때 최신 버전에 덮어쓴다. 저장소 YAML 은 DB 가 비어 있을 때의 첫 버전이기도 하다.
- **대체된 부분**: [ADR-005](superseded/005-ontology-yaml-server-validation.md) 의 「온톨로지는 Git 의 YAML 로 관리한다」 와 「웹은 정의를 읽기만 한다」 를 대체한다. 「API 가 쓰기를 검증하고 Cypher 에 넣는 이름은 허용 목록에서만 고른다」 는 그대로다.
- **대체된 부분(폼 편집기)**: 「ADMIN 만 웹의 폼 편집기와 YAML 편집기로 고친다」 의 폼 편집기는 [ADR-016](016-ontology-yaml-only-editor.md) 이 뺐다. 지금은 YAML 편집기 하나다. 에이전트가 올린 온톨로지 변경 제안을 ADMIN 이 승인하는 길은 [ADR-017](017-agent-ontology-and-instance-proposals.md) 이 더했다.
- **맥락**: 인물, 개념처럼 다룰 대상이 늘면서 타입과 관계 종류를 자주 더하게 됐다. YAML 을 고쳐 PR 과 재배포를 거치는 데 하루가 걸린다. 사용자는 ADMIN 이 웹에서 전체를 편집하기를 골랐다(2026-10-23). 기존 데이터와 어긋나는 변경은 영향받는 노드 수를 보여 준 뒤 허용하고, 키는 바꾸지 않고 표시 이름만 바꾸기로 했다.
- **대안 기각**:
  - 웹에서는 제안만 받고 반영은 YAML: 바꾸는 위험은 없지만 반영까지 재배포가 필요하다. 사용자가 고르지 않았다.
  - 더하기만 웹에서: 지우기와 고치기가 YAML 과 DB 두 곳에 나뉘어 어느 쪽이 맞는지 판단하기 어렵다.
  - 지금 버전 하나만 DB 에: 예전 버전으로 통째로 되돌리기가 어렵다.
  - 서버 코드와 맞물린 부분까지 웹에서 편집: 검토 상태나 Claim 의 속성을 지우면 서버 코드가 깨진다.
- **결과**:
  - 얻는 것: 재배포 없이 타입, 속성, 관계 종류, 주장 종류를 더하고 고친다. 모든 버전이 남아 누가 언제 무엇을 바꿨는지 보고 되돌릴 수 있다. 지금 버전을 YAML 로 내려받아 Git 에 백업할 수 있다.
  - 감당할 것: 기존 데이터와 어긋나는 정의가 저장될 수 있다. 어긴 노드는 고칠 때 새 규칙을 따른다. 저장소 YAML 의 편집할 수 있는 부분은 첫 버전을 만든 뒤로는 쓰지 않는다. 그래서 코드 변경이 새 타입을 필요로 하면 배포 뒤 웹에서 더하거나, YAML 편집기에 붙여 넣어 저장해야 한다. 온톨로지를 들고 있는 모든 서버 코드는 요청마다 최신 버전을 읽어야 한다.
- **적용 범위**: 저장 모델은 [데이터 스키마](../data-schema.md) 의 「온톨로지 버전」, 화면과 API 흐름은 [흐름](../flow.md) 의 「온톨로지 편집」, 계약은 [API 계약](../api-contract.md) 의 「온톨로지」 가 소유한다.
