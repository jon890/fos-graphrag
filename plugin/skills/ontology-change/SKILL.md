# 온톨로지 정의 바꾸기

**목표: 사용자가 확인한 변경만 제안으로 올리고, 반영되는 방법을 알린다.**

## 순서

| 단계 | 할 일 | 통과 조건 |
| --- | --- | --- |
| 1 | 바꿀 내용을 한 문장으로 확인받는다 | 사용자가 맞다고 답했다 |
| 2 | `get_ontology_yaml` 로 지금 정의와 버전을 받는다 | 정의와 `version` 을 받았다 |
| 3 | 필요한 곳만 고친다 | 확인받은 내용만 바뀌었다 |
| 4 | `propose_ontology_change` 로 올린다 | 도구 결과가 돌아왔다 |
| 5 | 거절되면 고쳐서 다시 올린다 | 올라갔거나, 세 번을 넘지 않고 멈췄다 |
| 6 | 승인 방법을 알린다 | 어디서 승인하는지 말했다 |

## 1. 바꿀 내용 확인

바꿀 내용을 한 문장으로 말하고 확인을 받습니다.

> 「인물」 종류에 「별명」 속성을 더하는 변경을 제안으로 올릴까요?

사용자가 답하기 전에는 올리지 않습니다.

## 2. 지금 정의 받기

`get_ontology_yaml` 을 부릅니다.
결과의 `version` 은 4 단계에서 `baseVersion` 으로 씁니다.

## 3. 필요한 곳만 고치기

확인받은 내용에 해당하는 부분만 고칩니다.

- 이미 있는 키의 이름은 바꾸지 않습니다. 이름을 바꾸면 기존 데이터와 어긋납니다.
- `reviewStatuses`, `changeActions`, `changeFields`, `claimRelationships`, `nodeTypes.Claim` 은 프로그램이 관리하는 부분이라 건드리지 않습니다.
- 사용자가 원하지 않은 정리나 재정렬은 하지 않습니다.

## 4. 올리기

`propose_ontology_change` 로 올립니다.

- `baseVersion`: 2 단계에서 받은 `version`
- `yaml`: 고친 정의 전체
- `rationale`: 바꾸는 까닭
- `note`: 한 줄 메모

## 5. 거절됐을 때

- `ONTOLOGY_INVALID`: 결과의 `details.errors` 에 줄 번호와 이유가 있습니다. 그 줄을 고쳐 다시 올립니다. 세 번까지 해 보고, 그래도 안 되면 막힌 이유를 사용자에게 말하고 멈춥니다.
- `REVISION_CONFLICT`: 그사이 다른 변경이 반영된 것입니다. 2 단계부터 다시 합니다.
- 「조회만 허락된 연결」 이라는 이유로 거절되면 `ontology-start` 스킬의 안내를 따릅니다.

## 6. 알리기

올라간 뒤에는 이렇게 알립니다.

> 워크벤치의 더보기 → 제안에서 바뀐 점과 영향을 보고 직접 승인해야 반영됩니다. 승인에는 관리자 역할이 필요합니다.

제안은 올린 사람만 보고 승인합니다. 다른 사람이 대신 승인한다고 안내하지 않습니다.

## 말하는 방식

- 어떤 종목을 사라거나 팔라는 권유는 하지 않습니다.
- 토큰이나 인증, 파일 문법 같은 내부 이야기는 꺼내지 않습니다. 오류는 어느 줄의 무엇이 틀렸는지만 말합니다.
