## ADR-013: 체결 기록은 주인만 보는 코드 소유 모델로 두고, 에이전트 쓰기는 사실은 바로 저장하고 해석은 제안으로 받는다

- **status**: `accepted`
- **결정**: 증권사 체결 기록은 지식 그래프 밖의 `(:User)-[:OWNS]->(:Trade)` 로 저장한다. `:Trade` 에는 `:Knowledge` label 이 없고 온톨로지가 정의하지 않는다. 주인만 읽고 지우며 ADMIN 도 남의 체결을 보지 않는다. 에이전트(Hermes)가 `/api/v1` 로 쓰는 것은 둘로 나눈다. 체결 사실은 `POST /api/v1/trades` 로 바로 저장하고, 같은 주인 안에서 `(broker, externalId)` 가 같으면 새로 만들지 않는다. 모델이 해석한 것(투자 결정 만들기, 관계 잇기, 체결과 결정 잇기, 공부 메모)은 `POST /api/v1/proposals` 로 `:Proposal` 에 담고 사람이 웹에서 승인한다. 승인하면 기존 서비스(노드 만들기, 관계 만들기, 이해 표시)로 실행해 기존 검증과 변경 이력을 그대로 탄다. 쓰기는 「조회와 기록」 범위(`READ_WRITE`)로 발급한 연동 토큰만 한다.
- **맥락**: 사용자는 토스증권 커넥터의 체결 기록을 금액과 수량까지 워크벤치에 넣고, 같은 Hermes 가 그 체결을 투자 결정과 잇게 하려 한다(사용자 결정 2026-10-25). 체결 금액과 수량은 개인 정보라 함께 쓰는 다른 사용자에게도 보이면 안 된다. 투자 결정, 밸류에이션 같은 지식은 지금처럼 로그인한 모두가 본다. 지식 조회(검색, 개념 지도 개수, 주변 그래프, 목록, 상세, 근거 따라가기)는 모두 `:Knowledge` label 로 노드를 고른다([ADR-011](011-learning-marks-and-trace.md) 의 `KNOWS` 와 같은 구조). 체결은 증권사가 확정한 사실이라 사람이 검토할 것이 없다. 모델이 체결을 보고 「이 매수는 이 결정을 실행한 것이다」 라고 해석한 것은 틀릴 수 있다.
- **ADR-012 와의 관계**: [ADR-012](012-agent-integration-token.md) 의 Bearer 전용 `/api/v1`, 세션 경로와의 분리, 토큰 저장 방식은 그대로다. 「`/api/v1` 에는 조회만 있다」 와 「토큰마다 범위를 두지 않는다」 는 이 결정이 바꾼다. 이미 발급한 토큰은 범위 속성이 없고 조회만 하는 것으로 읽는다. 쓰기 경로가 생겨도 토큰은 사용자 관리, 토큰 발급, 공유 지식의 직접 쓰기에 닿지 못한다.
- **대안 기각**:

  | 대안 | 기각 이유 |
  | --- | --- |
  | 체결을 `:Knowledge` 노드(온톨로지 타입 `Trade`)로 두고 조회마다 주인이 아닌 것을 뺀다 | 검색, 개수, 그래프, 목록, 상세, 근거 따라가기, 변경 이력, 온톨로지 영향 계산의 모든 쿼리에 주인 조건을 더해야 한다. 한 곳이라도 빠지면 남의 금액이 보인다. 온톨로지를 ADMIN 이 고칠 수 있어 필드와 규칙이 코드 밖에서 바뀐다 |
  | 에이전트의 모든 쓰기를 바로 저장한다 | 모델의 해석이 공유 지식(투자 결정, 관계)을 다른 사람의 확인 없이 바꾼다. 잘못 이은 관계를 사람이 찾아 보관해야 한다 |
  | 에이전트의 모든 쓰기를 제안으로 받는다 | 체결은 증권사가 확정한 사실이라 승인할 판단이 없다. 하루 체결 수만큼 승인할 일이 쌓이고, 승인 전에는 「내 체결」 과 투자 결정을 잇는 제안이 가리킬 체결이 없다 |
  | 제안을 승인할 때 별도 쓰기 코드로 실행한다 | 온톨로지 검증, 같은 종목 검사, 잠금, 변경 이력이 두 벌이 된다 |
  | 쓰기 경로를 기존 토큰에도 연다 | 조회용으로 넣어 둔 토큰이 사용자가 모르는 사이 기록 권한을 얻는다 |

- **결과**:
  - 얻는 것: 체결 기록은 `:Knowledge` 를 고르는 기존 조회에 처음부터 나오지 않는다. 주인 조건은 체결 저장소 한 곳에만 있다. 에이전트가 체결을 다시 보내도 하나만 남는다. 공유 지식은 사람이 승인한 것만 바뀌고, 승인한 사람이 변경 이력의 작업자로 남는다.
  - 감당할 것: `:Trade` 와 `:Proposal` 은 `:Knowledge` 가 아니어서, 지식 노드를 도는 쿼리는 양 끝을 `:Knowledge` 로 묶거나 경로 조건(`archived = false`)으로 이 노드를 지나지 않아야 한다. 그래서 체결과 제안, 그 관계에 `archived` 속성을 두지 않는다. 온톨로지 타입과 관계 이름에 `Trade`, `Proposal`, `OF_SECURITY`, `EXECUTES` 같은 코드 소유 이름을 쓸 수 없다. 체결은 변경 이력이 없어 지운 기록은 되살릴 수 없다. 제안의 내용은 만든 때의 온톨로지로 검사하고 승인할 때 다시 검사하므로, 그 사이 온톨로지가 바뀌면 승인이 실패하고 제안은 대기로 남는다. 열람자는 공유 지식을 만드는 제안을 승인하지 못해 편집자에게 부탁하거나 거절한다.
- **적용 범위**: 저장 모델은 [데이터 스키마](../data-schema.md) 의 「체결 기록」 과 「제안」, 계약은 [API 계약](../api-contract.md) 의 「내 체결」, 「제안」, 「에이전트 API(`/api/v1`)」 의 「쓰기」, 화면과 흐름은 [흐름](../flow.md) 의 「제안」, 「내 체결」, 「에이전트 쓰기」 가 소유한다.
