단일 Node

상태 전체를 새로 만들지 않고, 한 단계가 변경한 부분만 반환하는 계약을 익힌다.

오늘의 한 문장
Node는 현재 State를 읽고, 자신이 바꾼 키만 담은 업데이트를 반환한다.

1부 · 개념 학습

Node는 그래프의 작업 단위다

Node는 에이전트 전체를 의미하지 않는다. 현재 State를 읽고 하나의 좁은 책임을 수행하는 단계다. 일반 Java 메서드와 비슷하지만, 다음 Node를 직접 호출하지 않고 변경할 상태만 반환한다는 점이 다르다.

입력 현재 State 전체 ↓ Node가 필요한 값을 읽고 한 가지 작업 수행 ↓ 출력 변경된 키만 담은 부분 업데이트

부분 업데이트를 반환하는 이유

Node가 State 전체를 다시 만들면 자신이 책임지지 않는 값까지 복사하거나 덮어쓸 수 있다. 부분 업데이트를 반환하면 LangGraph4j가 각 키의 Channel 규칙으로 기존 State와 합친다.

Node의 책임

필요한 상태를 읽고 계산 결과를 부분 업데이트로 반환한다.

그래프 실행기의 책임

업데이트를 State에 병합하고 Edge를 따라 다음 Node를 실행한다.

처음에는 결정적인 Node로 연습한다

LLM 호출은 느리고 결과가 달라질 수 있다. 먼저 같은 입력에 항상 같은 결과를 내는 Java 로직으로 Node의 입력과 출력 계약을 익히면, 나중에 모델을 연결했을 때 문제의 원인을 분리하기 쉽다.

2부 · 실습 가이드

만들 동작

NormalizeRequestNode는 입력 요구사항의 앞뒤 공백을 정리하고, 비어 있다면 발견 사항 하나를 추가한다. 아직 LLM은 사용하지 않는다.

PlanningState 읽기 → request 정규화 → 변경된 request 또는 findings만 반환

직접 타이핑할 순서

  1. 가이드가 제공한 NormalizeRequestNodeTest를 실행해 기대 동작을 확인한다.
  2. NodeAction<PlanningState> 계약을 구현한다.
  3. 상태 접근자로 요구사항을 읽는다.
  4. 정규화 규칙을 작은 Java 로직으로 작성한다.
  5. 상태 객체를 직접 수정하지 않고 업데이트 맵을 반환한다.
  6. 제공된 테스트를 다시 실행하고 실패 메시지를 기준으로 운영 코드만 수정한다.

완료 조건

  • 제공된 NormalizeRequestNodeTest가 모두 통과한다.
  • 노드는 자신이 책임지지 않는 상태 키를 반환하지 않는다.
  • 같은 상태를 넣으면 항상 같은 업데이트가 나온다.
  • 노드가 Spring ApplicationContext 없이 생성된다.

생각할 질문

  • 노드가 PlanningState 전체를 반환하지 않는 이유는 무엇인가?
  • 빈 입력을 예외로 던지는 것과 상태에 기록하는 것은 그래프 흐름에 어떤 차이를 만들까?
  • 테스트가 그래프 전체를 만들지 않고 Node만 실행해도 되는 이유는 무엇인가?
막혔을 때 확인할 것
NodeAction.apply(...)의 입력과 반환 타입만 확인한다. 정규화 로직은 직접 결정한다.
