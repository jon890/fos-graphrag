# 제품 요구사항

## 목표

두 사람이 홈서버의 같은 화면에 접속해 기업, 종목, 관계와 근거를 함께 관리할 수 있게 한다.
금융 지식을 Neo4j 에 저장하고, 웹에서 탐색, 추가, 수정, 검토한다.

장기 흐름은 「금융 자료 수집 → 근거가 있는 지식그래프 → GraphRAG 검색 → FOS 투자 판단과 주문 제안 → 모의매매와 체결 추적 → 제한된 자동매매」 다.
이 문서가 다루는 첫 마일스톤은 그 가운데 근거가 있는 지식그래프를 사람이 관리하는 부분이다. GraphRAG 검색이나 자동매매를 구현하지 않는다.

## 만드는 것

- 온톨로지(타입, 속성, 관계, Claim predicate, 스키마 버전)를 Git 의 YAML 로 관리하고 웹에서 읽기 전용으로 보여 준다.
- Company, Security, Sector, Document, Claim 을 만들고 고친다. Company 와 Security 는 `ISSUES` 관계로 잇는다.
- 근거가 필요한 주장은 Claim 으로 만든다. Claim 은 근거 문서, 근거 문장, 유효 기간, 작성 방식, 검토 상태를 가진다.
- Google 계정 로그인, 허용 사용자 목록, `VIEWER`, `EDITOR`, `ADMIN` 역할과 사용자 관리 화면.
- 변경 이력, revision 기반 충돌 감지, 보관과 복원.
- 검색, 주변 그래프(기본 1홉, 최대 2홉), 표 목록, 검토 대기 목록, 변경 이력 화면.
- 운영 Compose, 개발 Compose, 백업과 복원 스크립트, 공개 HTTPS 경로 배포 문서, GHCR 이미지 workflow.

## 만들지 않는 것

- GraphRAG 검색, 임베딩, AI 추출, Ollama 컨테이너.
- 실시간 공동 커서, WebSocket 동기화.
- 웹에서 온톨로지 정의를 바꾸는 기능. 더한다면 `ADMIN` 만 한다.
- 공개 가입, 초대 메일, 조직 관리. 비밀번호 로그인.
- 외부 URL 을 서버가 가져오는 기능. 문서는 사람이 메타데이터를 등록한다.
- 증권 계좌, 주문, 토스증권 연동. 이것은 FOS Control Plane 과 Toss 커넥터의 책임이다.
- 실제 홈서버 배포.

## 요구가 충족됐다고 보는 관측

합성 데이터로 아래 흐름을 실행해 확인한다.

1. 사용자 A 가 기업과 종목을 등록한다.
2. 문서와 근거 문장을 등록하고 공급 관계 Claim 을 만든다.
3. 사용자 B 가 그 Claim 을 검토 완료로 바꾼다.
4. 검색과 주변 그래프에서 데이터, 근거, 검토자를 확인한다.
5. 두 사용자가 같은 revision 을 고치면 두 번째 저장이 409 로 안내된다.
6. 보관과 복원이 이력에 남는다.
7. Compose 를 내렸다 올려도 데이터가 남는다.

자동 테스트로 확인하는 것은 다음과 같다.

- 허용하지 않은 타입, 관계, 속성을 거절한다.
- 인증 없는 조회와 변경을 막는다.
- 실제 Neo4j 에서 동시 수정이 하나만 성공한다.
- 데이터 변경과 이력 기록이 함께 커밋되거나 함께 롤백된다.
- 보관한 데이터가 기본 검색에서 빠진다.
- 주변 그래프의 홉 수와 결과 개수가 제한된다.
- 위 흐름 1~6 을 브라우저에서 실행한다.

## 남은 한계

- Google `sub` 묶음을 푸는 관리 기능이 없다. 사용자가 Google 계정을 바꾸면 운영자가 Neo4j 에서 그 사용자의 `googleSub` 을 직접 지워야 한다.
- 유효 기간의 「미상」 은 값을 비워 두는 것으로만 표현한다. 「확인했으나 모름」 과 「아직 입력하지 않음」 을 가르지 않는다.
- 세션은 API 프로세스 메모리에 있다. API 를 재시작하면 다시 로그인한다.
- 실제 Google 로그인은 배포한 뒤 사람이 확인한다. 자동 테스트와 브라우저 테스트는 가짜 OIDC 공급자를 쓴다.
- 스키마 초기화는 웹 서버가 요청을 받기 전에 끝난다. 초기화가 실패하면 API 가 시작하지 않고 health 도 응답하지 않는다.

## FOS 연동 경계

| 영역 | 책임 |
| --- | --- |
| 이 워크벤치(GraphRAG 쪽) | 금융 지식, 근거, 시점, revision, 검색 |
| FOS Control Plane | 사용자, 계좌 권한, 승인, 전략 정책, 주문, 체결 |
| Toss 커넥터(`fos-assistant`) | 공식 API 인증, 조회, 실행 |

공유 지식그래프의 편집 권한과 개인 증권계좌의 실행 권한은 따로 둔다.
개인 계좌 키, 잔고, 주문 내역은 이 그래프에 넣지 않는다. 온톨로지에도 그런 타입이 없다.
후속 도구가 쓸 응답 필드는 [API 계약](api-contract.md)의 「후속 도구가 쓸 필드」 절에 있다.
관련 후속 과제는 https://github.com/jon890/fos-assistant/issues/593 이다.

## 다음 GraphRAG 마일스톤

이번 마일스톤에서는 구현하지 않는다. 다음 단계의 범위만 정의한다.

| 단계 | 하는 일 | 이번 구조에서 이어 쓰는 것 |
| --- | --- | --- |
| 문서 분할 | 등록된 Document 의 원문을 사람이 올리거나 허용된 출처에서 받아 문단 단위 `:Chunk` 로 나눈다. Chunk 는 Document 와 `PART_OF` 로 잇고 위치(시작, 끝 오프셋)를 가진다 | Document 의 `id`, `url`, `publishedAt`, `collectedAt` |
| 개체 연결 | Chunk 에 나온 기업명과 종목 코드를 기존 Company, Security 의 `id` 에 연결한다. 확신이 낮은 연결은 후보로만 남긴다 | `security_listing_unique` 와 `searchText` |
| 검토 대기 Claim 추출 | 모델이 Chunk 에서 온톨로지 predicate 에 맞는 Claim 을 뽑아 `authoringMethod = AI`, `reviewStatus = DRAFT`, `extractionConfidence` 를 채워 저장한다. 사람이 검토 대기 화면에서 승인한다 | Claim 스키마, 검토 API, 온톨로지 검증기 |
| 근거 기반 검색 | 질문을 받아 Chunk 임베딩 검색과 그래프 이웃 탐색을 합친다. 기본은 `REVIEWED` Claim 만 쓴다 | 주변 그래프 API 의 한도 정책 |
| 출처를 포함한 답변 생성 | 답변마다 사용한 Claim 의 `id`, `revision`, Document `url`, 근거 문장을 붙인다. 근거가 없으면 답하지 않는다 | `get_evidence` 가 쓸 `ClaimView` |

이 단계에서 Ollama 와 임베딩 모델을 Compose 에 넣을지는 홈서버 자원을 확인한 뒤 정한다.
