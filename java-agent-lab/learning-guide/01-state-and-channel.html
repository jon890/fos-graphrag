Lesson 01

State와 Channel

노드보다 먼저, 그래프를 흐르는 데이터와 각 값의 병합 규칙을 정의한다.

오늘의 한 문장
State는 공유 데이터이고, Channel은 같은 키에 새 값이 들어왔을 때 합치는 규칙이다.

1부 · 개념 학습

State는 현재 실행 상황을 나타낸다

State는 그래프가 현재 어디까지 실행되었고 어떤 데이터를 가지고 있는지를 나타낸다. 각 Node는 현재 State를 읽어 작업하고, 자신이 변경하려는 값만 부분 업데이트로 반환한다. LangGraph4j는 이 업데이트를 기존 State에 반영해 다음 State를 만든다.

현재 State ↓ Node가 필요한 값을 읽음 Node가 부분 업데이트를 반환 ↓ LangGraph4j가 기존 값과 병합 다음 State ↓ Edge를 따라 다음 Node로 전달

LangGraph4j에서는 AgentState로 표현한다

LangGraph4j에서는 보통 AgentState를 상속해 그래프에 필요한 상태 클래스를 정의한다. AgentState는 키와 값으로 구성된 상태 데이터를 보관하고, 키로 값을 읽는 기능을 제공한다. 우리 실습에서는 사용할 키, 값을 읽는 접근자와 Channel 스키마를 PlanningState에 함께 두어 그래프의 상태 계약을 한곳에서 확인할 수 있게 한다.

Node는 State 전체를 교체하지 않는다

Node가 State에 있는 모든 값을 다시 반환할 필요는 없다. 자신이 변경한 키만 반환한다. 변경하지 않은 키는 기존 값을 유지한다. 이 방식을 사용하면 각 Node가 자신의 책임에 해당하는 상태만 다룰 수 있다.

Channel은 부분 업데이트를 합치는 규칙이다

부분 업데이트가 들어오면 LangGraph4j는 기존 값과 새 값을 어떻게 합칠지 결정해야 한다. 이 키별 병합 정책이 Channel이다. Channel은 별도로 실행되는 Node가 아니며, 이번 실습에서 새로운 Channel 클래스를 직접 구현하지도 않는다. 상태 스키마에서 LangGraph4j가 제공하는 Channel을 각 키에 지정한다.

Channels.base(...)

리듀서 없이 새 값으로 기존 값을 교체한다. 하나의 최신 값만 유지해야 하는 상태에 사용한다.

Channels.appender(...)

기존 목록에 중복되지 않는 새로운 결과를 붙인다. 여러 Node의 결과를 모아야 하는 상태에 사용한다.

Channel 선택은 상태 스키마에 기록한다

LangGraph4j의 그래프는 상태 키와 Channel의 관계를 담은 스키마를 사용한다. 우리 실습에서는 Map<String, Channel<?>> 형태의 정적 스키마를 PlanningState에 선언한다. 이 맵에 각 키가 사용할 Channel을 등록하는 것이 “Channel을 선택한다”는 의미다.

상태 스키마 request → Channels.base(() -> "") findings → Channels.appender(ArrayList::new)

LangGraph4j가 문자열이나 목록 자료형만 보고 Channel을 자동으로 결정하는 것은 아니다. 같은 목록이라도 최신 목록 하나만 유지할 수도 있고 여러 결과를 누적할 수도 있으므로, 상태를 설계하는 사람이 그 키의 의미에 맞춰 직접 지정한다.

SCHEMA는 자동 등록되지 않는다
AgentState에는 스키마를 지정하는 속성이나 메서드가 없다. PlanningState에 SCHEMA를 두는 것은 상태 정의를 한곳에 모으기 위한 설계다. 실제 연결은 Lesson 03에서 StateGraph를 생성할 때 Channel 스키마와 PlanningState를 만드는 상태 팩터리를 함께 전달하면서 이루어진다.
PlanningState.SCHEMA + PlanningState::new ↓ StateGraph 생성 ↓ CompiledGraph가 초기값 생성과 부분 업데이트 병합에 SCHEMA 사용
변경 가능한 기본 목록
Channels.appender(...)는 기존 목록에 값을 추가한다. 따라서 기본값 공급자는 List.of()가 아니라 ArrayList::new처럼 변경 가능한 목록을 만들어야 한다.

initData와 Channel 기본값은 역할이 다르다

initData

그래프를 실행할 때 호출자가 넘긴 실제 시작 데이터다. 생성자는 이 값을 AgentState에 전달한다.

Channel 기본값 공급자

해당 키의 기존 값이 없을 때 Channel이 병합을 시작하기 위해 사용할 값을 만드는 규칙이다.

생성자가 입력 Map에 기본값을 직접 넣으면 호출자가 소유한 데이터를 변경하게 된다. AgentState 생성자는 입력 데이터를 내부 Map으로 복사하므로, PlanningState 생성자는 전달만 담당한다. 값이 없는 상태를 읽을 때의 안전한 기본값은 접근자의 Optional.orElse(...)에서 처리한다.

호출자가 initData 전달 ↓ 생성자는 AgentState에 그대로 전달 PlanningState 생성 ↓ 값이 없으면 접근자가 빈 값으로 안전하게 읽음 Node가 findings 업데이트 반환 ↓ SCHEMA의 appender가 ArrayList 기본값에서 누적 시작 다음 State 생성
기존 상태의 특정 키 값 + Node가 반환한 새 값 ↓ 그 키의 Channel ↓ 다음 State의 값

실습 예제에 적용한다

앞으로 만들 예제는 개발 요구사항을 여러 관점에서 검토하는 그래프다. 이 그래프의 상태 클래스 이름을 PlanningState로 정하고, 첫 단계에서는 request와 findings 두 키만 사용한다.

request는 덮어쓰기

요구사항을 정규화하거나 수정하면 최신 문장 하나만 남아야 한다. 이전 문장과 새 문장을 목록으로 누적할 필요가 없다.

findings는 누적

요구사항·아키텍처·테스트 검토가 각각 발견한 내용을 모두 보존해야 한다. 새 결과가 이전 결과를 지우면 안 된다.

request 기존: " 로그인 기능 " 갱신: "로그인 기능" base 결과: "로그인 기능" findings 기존: ["요구사항이 모호함"] 갱신: ["테스트 조건이 없음"] appender 결과: ["요구사항이 모호함", "테스트 조건이 없음"]

이번 단계에서 만드는 것과 만들지 않는 것

직접 만든다

PlanningState, 상태 키, 키별 Channel 스키마와 값을 읽는 접근자를 작성한다.

직접 만들지 않는다

Channel 구현체, Node, Edge, 그래프, Spring Bean은 아직 만들지 않는다.

이번 단계의 범위

planning 패키지에 PlanningState만 만든다. 테스트, 그래프, Node, Edge, Spring Bean은 아직 만들지 않는다.

설계할 상태

request

사용자가 입력한 개발 요구사항이다. 문자열이며 새로운 값이 오면 덮어쓴다.

findings

검토 과정에서 발견한 내용이다. 문자열 목록이며 여러 결과를 누적한다.

직접 타이핑할 순서

  1. AgentState를 상속하는 상태 클래스를 만든다.
  2. 두 상태 키를 문자열 상수로 선언한다.
  3. 상태 타입 전체가 공유할 static final Map<String, Channel<?>> 스키마를 선언한다.
  4. 스키마에서 request 키를 Channels.base(...)에 연결한다.
  5. 스키마에서 findings 키를 Channels.appender(...)에 연결한다.
  6. 초기 데이터 맵을 상위 생성자에 전달하는 생성자를 만든다.
  7. 두 값을 읽기 위한 좁은 접근자를 만든다.

완료 조건

  • 상태 키 문자열이 접근자 곳곳에 중복되지 않는다.
  • 값이 없는 상태를 읽어도 예외가 발생하지 않는다.
  • request와 findings의 Channel이 상태 스키마에 명시되어 있다.
  • 왜 두 키에 서로 다른 Channel을 사용했는지 말로 설명할 수 있다.
  • PlanningState가 컴파일된다.

생각할 질문

  • request도 누적 채널로 만들면 어떤 잘못된 상태가 생길까?
  • 상태 접근자가 원시 맵을 그대로 노출하면 노드 코드가 어떻게 달라질까?
  • 리듀서는 필드의 자료형인가, 갱신 정책인가?
막혔을 때 확인할 것
AgentState, Channel, Channels.base(...), Channels.appender(...)의 생성 형태만 확인한다. 완성된 상태 클래스를 복사하지 않는다.
