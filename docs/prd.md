# 제품 요구사항

## 목표

두 사람이 홈서버의 같은 화면에 접속해 각자의 투자 논리를 그래프로 남기고 함께 본다.
투자 논리는 「세상의 변화 → 병목 → 병목이 있는 산업 → 이익을 가져가는 기업 → 시나리오 밸류에이션 → 투자 결정」 으로 이어진다. 이 구조를 투자 온톨로지라 부른다. 하방이 막히고 상방이 열린 기업을 고르는 판단을, 나중에 결정에서 변화까지 거슬러 따라갈 수 있게 남기는 것이 목적이다([ADR-009](adr/009-investment-logic-chain.md)).
이 지식을 Neo4j 에 저장하고, 웹에서 탐색, 추가, 수정, 검토한다.

장기 흐름은 「금융 자료 수집 → 근거가 있는 지식그래프 → GraphRAG 검색 → FOS 투자 판단과 주문 제안 → 모의매매와 체결 추적 → 제한된 자동매매」 다.
이 문서가 다루는 첫 마일스톤은 그 가운데 근거가 있는 지식그래프를 사람이 관리하는 부분이다. GraphRAG 검색이나 자동매매를 구현하지 않는다.

## 방향

최종 목표는 토스증권(tossinvest)과 가치투자 온톨로지를 합쳐, 기록한 투자 논리에서 실제 매매까지 잇는 것이다(사용자 결정 2026-10-26). 단계는 아래 순서다.

| 단계 | 하는 일 | 상태 |
| --- | --- | --- |
| 지금 | 친구가 Claude Code, Codex 로 온톨로지와 인스턴스를 조회하고 고친다. 고치는 일은 제안으로 받아 사람이 승인한다 | 이 문서의 범위 |
| 다음 | 개인 비서(Hermes, fos-assistant)를 같은 `/mcp` 와 제안 계약에 붙인다. 서버의 연동 토큰과 `/api/v1` 은 이 단계를 위해 남긴다 | 길만 열어 둔다 |
| 그다음 | 증권사 연동과 매매. 체결 기록과 투자 결정을 이어 주문 제안까지 간다 | 만들지 않는다 |


## 만드는 것

- 온톨로지(타입, 속성, 관계, Claim predicate)를 모든 역할에게 보여 준다. ADMIN 은 웹의 YAML 편집기로 고치거나, 에이전트가 올린 온톨로지 변경 제안을 승인한다([ADR-016](adr/016-ontology-yaml-only-editor.md)). 저장 전에 바뀐 점과 기존 데이터에 주는 영향을 보고, 저장할 때마다 버전이 쌓여 예전 버전으로 되돌리고 YAML 로 내려받을 수 있다.
- 투자 온톨로지의 노드(세상의 변화, 병목, 밸류에이션, 시나리오, 투자 결정)를 만들고, 산업, 기업, 종목, 근거 자료와 일반 관계로 잇는다. 만들기 창의 시작 노드 고르기 칸으로 앞 노드를 고르며 이어 간다.
- 친구가 정리한 투자 기록을 초기 데이터로 옮긴다. 메모리 병목, 데이터센터 전력, 칩 사이 광 연결의 변화와 병목, FLNC 의 밸류에이션, 세 종목(SK하이닉스, FLNC, POET)의 결정 넷이다.
- Company, Security, Sector, Document, Claim 을 만들고 고친다. Company 와 Security 는 `ISSUES` 관계로 잇는다. 주장은 산업 소속(`BELONGS_TO_SECTOR`)과 거장의 생각(`ADVOCATES`, `CRITICIZES`)만 남긴다.
- 거장의 생각을 담을 수 있다. 인물(Person)과 개념(Concept)을 만들고, 「인물 → 개념 강조한다」 같은 주장에 짧은 인용과 출처(책, 서한, 강연)를 붙인다. 인물의 초기 데이터는 없다. 개념은 기본 투자 개념 몇 가지를 초기 데이터로 넣고 투자 온톨로지 항목과 「쓰는 개념」 관계로 잇는다.
- 근거가 필요한 주장은 Claim 으로 만든다. Claim 은 근거 문서, 근거 문장, 유효 기간, 작성 방식, 검토 상태를 가진다.
- Google 계정 로그인, 허용 사용자 목록, `VIEWER`, `EDITOR`, `ADMIN` 역할과 사용자 관리 화면.
- 변경 이력, revision 기반 충돌 감지, 보관과 복원. 노드를 동시에 고쳐 저장이 거절돼도 내 입력은 남고, 칸마다 내 값과 최신 값 가운데 고른다.
- 만들기 폼의 입력 도움. 같은 이름 경고와 구분 정보, 국가와 통화 목록, 주소 앞 `https://` 자동 붙임, 수집 시각 기본값, 종목을 만들며 발행 기업 잇기.
- 첫 화면의 개념 지도. 온톨로지의 타입과 관계를 그림으로 보이고 타입마다 등록한 항목 수를 붙인다. 타입을 누르면 설명, 최근 항목, 이어지는 관계 문장, 그 타입의 「＋ 추가」 가 나온다.
- 상단 탭은 개념 지도, 작업 공간, 목록, 공부 넷이다. 나머지 화면은 「더보기」 메뉴에 역할별로 있다. 목록은 [흐름](flow.md) 「주소와 뒤로가기」 의 표가 소유한다.
- 모든 화면의 같은 자리에 있는 「＋ 추가」. 타입을 고르면 필수 칸만 먼저 보이는 만들기 창이 열린다.
- 검색, 주변 그래프(기본 1홉, 최대 2홉), 표 목록, 검토 대기 목록, 변경 이력 화면. 작업 공간의 검색 칸은 검색창과 종류 칩만 보이고 나머지 조건은 「고급 필터」 에 접혀 있다.
- 작업 공간 상세는 읽기 카드다. 속성은 이름과 값, 관계는 문장으로 보이고, 「편집」 을 눌러야 편집 폼이 열린다.
- 검토 대기는 「내가 검토할 주장」 과 「내가 쓰거나 고친 주장」 으로 나눈다. 항목마다 「링크 복사」 가 있어 링크로 다른 편집자에게 검토를 부탁한다.
- 변경 이력은 칸 이름과 값을 한국어로 보이고, 노드 ID 는 이름으로 보인다. 대상은 이름으로, 사용자는 표시 이름으로 골라 좁혀 본다.
- 주장을 문장 채우기 폼으로 만든다. 「＋ 추가」 와 항목 상세 양쪽에서 시작하고, 주체와 대상을 맞바꿀 수 있다.
- 그래프는 기본으로 주장을 「주체 → 대상」 선 하나로 접어 보여 주고, 주장을 노드로 펼쳐 볼 수도 있다. 주장의 이름은 「주체 → 대상 관계」 다.
- 화면 상태를 주소에 둔다. 상단 탭은 경로, 연 항목과 검색 조건은 query 다. 뒤로가기와 앞으로가기가 탭 이동, 항목 열기, 휴대폰의 검색, 그래프, 상세 탭 사이를 오가고, 새로고침과 링크가 보던 화면을 다시 연다.
- 근거 따라가기. 항목 하나에서 들어오는 관계를 거꾸로 따라가며 단계마다 근거 문서, 주장과 검토 상태, 쓰는 개념, 근거 상태(근거 있음, 초안 주장만, 근거 없음)를 보인다. 아직 잇지 않은 관계(예: 결정에 밸류에이션이 이어지지 않음)를 후보와 함께 알리고 편집자는 그 자리에서 잇는다. 이 항목에 기대는 항목도 한 단계 보인다.
- 내 이해 표시와 공부 목록. 항목마다 「알아요」, 「잘 모르겠어요」 와 메모를 남기고, 「공부」 탭에서 모르는 항목을 단계 맥락과 할 일(근거 문서 읽기, 개념 설명 읽기, 자료 붙이기)과 함께 본다. 투자 결정마다 근거를 다 이해했는지 세어 「내 능력 범위」 로 보인다. 표시는 본인만 보고 열람자도 남긴다.
- 개념 설명 연결. 항목에 「쓰는 개념」 관계로 이은 개념을 상세와 근거 따라가기의 칩으로 보이고, 칩에서 한 줄 정의를 읽는다. 개념 상세는 강조한 사람, 비판한 사람, 관련 개념, 이 개념을 쓴 곳을 보인다.
- 에이전트 조회. 사용자가 더보기 메뉴의 「연동」 의 「연동 토큰」 에서 개인 연동 토큰을 발급하고 폐기한다. 개인 비서 Hermes(fos-assistant)는 그 토큰으로 `/api/v1` 의 조회 API(온톨로지, 검색, 상세, 근거 따라가기, 주변 그래프, 종목 코드로 결정과 밸류에이션 찾기, 토큰 주인의 공부 목록, 내 체결과 제안)를 부른다([ADR-012](adr/012-agent-integration-token.md)).
- 에이전트 기록. 「조회와 기록」 범위로 발급한 토큰으로 Hermes 가 토스증권 체결을 금액과 수량까지 넣는다. 같은 체결은 한 번만 저장한다. 항목 만들기와 고치기와 보관, 관계 잇기와 보관, 주장 만들기, 온톨로지 바꾸기, 체결과 결정 잇기, 공부 메모처럼 모델이 해석한 것은 제안으로 올라오고, 사용자가 더보기의 「제안」 에서 값을 고쳐 승인하거나 거절한다. 승인한 것만 기존 검증과 변경 이력을 거쳐 저장된다. 공유 지식을 바꾸는 제안은 편집자만, 온톨로지 변경 제안은 관리자만 승인한다([ADR-013](adr/013-owner-trades-and-agent-proposals.md), [ADR-017](adr/017-agent-ontology-and-instance-proposals.md)).
- 비개발자의 앱 연결. 친구가 Claude Code 나 Codex 에 이 저장소의 플러그인(`plugin/`)을 설치하면, 스킬이 연결 확인부터 이끌고 처음 도구를 부를 때 브라우저가 열린다. Google 로그인과 동의 화면의 「연결 허용」 한 번이면 원격 MCP(`/mcp`)의 도구로 온톨로지를 조회하고 체결을 기록하고, 인스턴스와 온톨로지 정의를 바꾸는 제안을 올린다. 「연동」 화면 맨 위가 두 앱의 설치 단계를 복사 단추와 함께 보인다. 토큰을 복사하지 않는다. 더보기의 「연동」 에서 연결된 앱을 보고 끊는다. 도구는 서버 한 곳에 있고 Hermes 도 연동 토큰으로 같은 `/mcp` 를 부른다([ADR-015](adr/015-remote-mcp-oauth.md)).
- 내 체결. 체결 기록은 주인만 본다. 더보기의 「내 체결」 화면, 종목과 투자 결정 상세의 「내 체결」 절, 근거 따라가기의 투자 결정 단계에 「실행한 체결」 이 있고 다른 사용자에게는 보이지 않는다.
- 첫 접속 가이드. 처음 로그인한 편집자는 말풍선을 따라 「＋ 추가」 에서 연습 기업, 근거 문서, 주장을 직접 만들어 보고, 끝나면 연습 항목은 보관된다. 열람자는 개념 지도, 검색, 그래프, 상세를 둘러보는 가이드를 본다. 머리글의 「사용법」 으로 다시 본다.
- 휴대폰에서도 쓸 수 있는 화면. 폭 1024px 미만에서는 작업 공간을 검색, 그래프, 상세 탭으로 나눈다.
- 운영 Compose, 개발 Compose, 백업과 복원 스크립트, 공개 HTTPS 경로 배포 문서, GHCR 이미지 workflow.

## 친구가 대화로 하는 일

친구는 Claude Code 와 Codex 를 1순위로 쓴다(사용자 결정 2026-10-26). 아래는 플러그인 도구와 스킬로 친구가 대화만으로 할 수 있는 일과, 지금 역할 규칙에서 누가 끝내는지다.
제안은 올린 사람의 것이라 승인도 친구 본인이 웹의 「제안」 에서 한다([ADR-013](adr/013-owner-trades-and-agent-proposals.md), [ADR-017](adr/017-agent-ontology-and-instance-proposals.md)). 친구의 역할은 `ADMIN` 으로 둔다(사용자 결정 2026-10-26). 승인 규칙은 바꾸지 않는다. 운영에서 역할을 바꾸는 일은 사용자가 웹의 「사용자」 화면에서 한다.

| 일 | 스킬 | 도구 | 제안 종류 | 승인에 필요한 역할 | 친구 혼자 끝내나 |
| --- | --- | --- | --- | --- | --- |
| 처음 시작(연결, 역할과 범위 확인, 온톨로지 한눈에 보기, 첫 데이터 추가 연습) | `ontology-start` | `get_connection`, `get_ontology`, `submit_proposals` | `CREATE_NODE` | `EDITOR` | 예 |
| 개념, 투자 근거, 내 공부 목록 조회 | `ontology-explore` | `search_nodes`, `get_node`, `trace_node`, `get_neighborhood`, `lookup_security`, `list_my_knowledge` | 없음 | 없음 | 예. 모든 역할 |
| 항목(노드) 만들기, 근거 문서 만들기 | `ontology-record` | `submit_proposals` | `CREATE_NODE` | `EDITOR` | 예 |
| 항목 속성 고치기 | `ontology-record` | `get_node`, `submit_proposals` | `UPDATE_NODE` | `EDITOR` | 예 |
| 항목 보관 | `ontology-record` | `get_node`, `submit_proposals` | `ARCHIVE_NODE` | `EDITOR` | 예 |
| 관계 잇기, 근거 문서 잇기 | `ontology-record` | `submit_proposals` | `CREATE_RELATIONSHIP` | `EDITOR` | 예 |
| 관계 보관 | `ontology-record` | `get_node`, `submit_proposals` | `ARCHIVE_RELATIONSHIP` | `EDITOR` | 예 |
| 주장 만들기 | `ontology-record` | `submit_proposals` | `CREATE_CLAIM` | `EDITOR` | 만들기는 예. 검토는 작성자(승인한 친구)가 할 수 없어 사용자가 한다 |
| 온톨로지 정의 바꾸기 | `ontology-change` | `get_ontology_yaml`, `propose_ontology_change` | `ONTOLOGY_CHANGE` | `ADMIN` | 친구가 `ADMIN` 이면 예 |
| 체결 기록, 체결과 결정 잇기, 공부 메모 | `ontology-record` | `record_trades`, `submit_proposals` | `LINK_TRADE_DECISION`, `STUDY_NOTE` | `VIEWER` | 예 |

- 쓰기 도구는 로그인할 때 「조회와 기록」 을 고른 연결에서만 된다.
- 친구가 `EDITOR` 면 온톨로지 변경 제안을 올릴 수는 있지만 아무도 승인하지 못한다. 제안은 올린 사람만 보기 때문이다.
- 주장 내용 고치기와 검토, 보관한 것 되살리기는 아직 웹에서만 한다.

## 만들지 않는 것

- GraphRAG 검색, 임베딩, AI 추출, Ollama 컨테이너.
- 실시간 공동 커서, WebSocket 동기화.
- 공개 가입, 초대 메일, 조직 관리. 비밀번호 로그인.
- 외부 URL 을 서버가 가져오는 기능. 문서는 사람이 메타데이터를 등록한다.
- 기업 사이의 공급, 경쟁, 노출 관계. 거시경제 이론.
- 하방률, 상방률, 비대칭 배수 같은 밸류에이션 계산값. 시나리오의 가치는 사람이 넣는다.
- 체결 기록 밖의 열람 제한. 투자 결정과 밸류에이션도 로그인한 모든 사용자가 본다. 본인만 보는 것은 이해 표시와 메모, 체결 기록, 제안이다.
- 증권 계좌, 주문, 토스증권 연동. 이것은 FOS Control Plane 과 Toss 커넥터의 책임이다. 워크벤치는 커넥터가 가져온 체결 결과만 받고 계좌 번호와 잔고는 받지 않는다.
- 에이전트가 공유 지식을 바로 쓰는 것. 체결 밖의 쓰기는 모두 제안을 거친다.
- 웹에서 체결을 직접 입력하거나 고치는 화면, 체결과 결정의 연결을 끊는 화면.
- Hermes 커넥터 자체. 커넥터는 fos-assistant 저장소가 이 문서의 `/api/v1` 계약을 따라 만든다. fos-assistant 가 이 저장소의 플러그인과 `/mcp` 로 옮기는 일도 그 저장소의 몫이다.
- 클라이언트 ID 메타데이터 문서(CIMD)와 미리 등록한 OAuth 클라이언트. 클라이언트는 동적 등록으로만 붙는다.
- 다른 서비스가 이 서버의 OAuth 로 로그인하는 것. 인가 서버는 `/mcp` 하나를 위한 것이다.
- 실제 홈서버 배포.

## 요구가 충족됐다고 보는 관측

합성 데이터로 아래 흐름을 실행해 확인한다.

1. 사용자 A 가 기업과 종목을 등록한다.
2. 문서와 근거 문장을 등록하고 산업 소속 Claim 을 만든다.
3. 사용자 B 가 그 Claim 을 검토 완료로 바꾼다.
4. 검색과 주변 그래프에서 데이터, 근거, 검토자를 확인한다.
5. 두 사용자가 같은 revision 을 고치면 두 번째 저장이 409 로 안내된다. 두 번째 사용자는 자기 입력을 다시 적용해 저장할 수 있다.
6. 보관과 복원이 이력에 남는다.
7. Compose 를 내렸다 올려도 데이터가 남는다.
8. 사용자 A 가 세상의 변화, 병목, 기업, 밸류에이션과 시나리오, 투자 결정을 차례로 만들며 앞 노드를 고르고, 결정의 주변 그래프에서 「이웃 확장」 으로 변화까지 따라간다.

자동 테스트로 확인하는 것은 다음과 같다.

- 허용하지 않은 타입, 관계, 속성을 거절한다.
- 인증 없는 조회와 변경을 막는다.
- 실제 Neo4j 에서 동시 수정이 하나만 성공한다.
- 데이터 변경과 이력 기록이 함께 커밋되거나 함께 롤백된다.
- 보관한 데이터가 기본 검색에서 빠진다.
- 주변 그래프의 홉 수와 결과 개수가 제한된다.
- 위 흐름 1~6 을 브라우저에서 실행한다.
- 1홉 주변 그래프에서 산업 소속 주장이 기업과 산업 사이의 선 하나로 보이고, 선을 누르면 그 주장의 상세와 근거가 열린다.
- 산업의 상세에서 시작해 「주체와 대상 바꾸기」 로 그 산업에 속하는 기업의 주장을 만든다.
- 위 흐름 8 을 브라우저에서 실행한다. 결정 폼의 「결정한 종목」 과 「결정에 쓴 밸류에이션」 을 고르면 두 관계가 함께 생긴다.
- 초기 데이터를 적용하면 FLNC 의 결정에서 종목, 기업, 병목, 변화까지 관계가 이어져 있고, 그 기업에 밸류에이션 둘과 시나리오 여섯이 붙어 있다. 친구 자료에서 결정이 어느 밸류에이션을 썼는지는 확인되지 않아 결정과 밸류에이션은 잇지 않았다.
- 폭 390px 화면에서 가로 스크롤 없이 검색, 그래프, 상세 탭을 오가며 노드를 고르고 상세를 연다. 머리글의 탭 넷과 「더보기」, 「＋ 추가」 가 한 줄에 들어간다.
- 처음 열면 개념 지도가 보이고, 타입마다 보관하지 않은 항목 수가 붙는다. 타입을 고르면 최근 항목과 관계 문장이 나오고 「＋ {타입} 추가」 로 그 타입의 만들기 창이 열린다.
- 편집자가 「＋ 추가」 에서 타입을 골라 필수 칸만 채워 저장하면 작업 공간에서 새 항목의 상세가 열린다. 열람자에게는 「＋ 추가」 가 없다.
- 작업 공간의 상세는 읽기 카드로 열리고 「편집」 을 눌러야 편집 폼이 열린다. 고급 필터는 접혀 있고, 바꾼 조건의 개수를 머리에 보인다.
- 더보기 메뉴의 항목이 역할별로 보인다. 열람자에게 「검토 대기」 와 「사용자」 가 없고, 편집자에게 「사용자」 가 없다.
- 처음 로그인한 편집자가 가이드를 끝까지 따라 하면 연습 기업, 근거 문서, 주장이 만들어졌다가 보관되고, 다시 로그인해도 가이드가 열리지 않는다. 열람자는 둘러보기를 건너뛸 수 있다.
- FLNC 첫 매수의 근거 따라가기가 종목, 기업, 병목, 변화와 산업까지 단계를 보이고, 단계마다 근거 상태와 근거 문서를 보인다. 결정에 밸류에이션이 이어지지 않았다는 안내와 같은 기업의 밸류에이션 후보가 보이고, 편집자가 후보를 이으면 다시 읽은 화면에 그 밸류에이션 단계가 생긴다.
- 사용자 A 가 근거 따라가기에서 단계 하나를 「잘 모르겠어요」 로 표시하고 메모를 남기면 공부 탭에 그 항목이 단계 맥락과 함께 나오고, 「이해했어요」 를 누르면 목록에서 빠지고 이해함 수가 는다. 사용자 B 의 화면에는 A 의 표시가 보이지 않는다. 열람자도 표시를 남긴다.
- 개념을 쓰는 항목의 상세와 근거 따라가기에 개념 칩이 보이고, 칩에서 한 줄 정의를 읽고 개념 상세를 연다. 개념 상세에 「이 개념을 쓴 곳」 이 보인다.
- 폭 1440px 개념 지도에서 노드 이름이 13px 이상으로 그려진다.
- 사용자가 「연동」 의 「연동 토큰」 에서 이름을 붙여 토큰을 발급하면 원문이 한 번 보이고 「복사」 로 클립보드에 들어간다. 창을 닫으면 목록에 이름, 만든 때, 끝 네 자리만 남는다. 폐기하면 목록에서 빠진다. 폭 1440px 와 390px 에서 확인한다.
- 그 토큰으로 `GET /api/v1/ontology` 가 `200` 이다. 토큰이 없거나 틀리거나 폐기됐거나 주인이 비활성이면 `401`, 세션 쿠키만으로 부르면 `401`, 토큰으로 세션 API(`/api/nodes`)를 부르면 `401` 이다. `/api/v1` 에 계약에 없는 쓰기 메서드를 보내면 `405` 나 `404` 다. 1분에 61번째 요청은 `429` 다.
- 「조회와 기록」 토큰으로 같은 체결을 두 번, 또는 동시에 보내도 체결은 하나다. 「조회만」 토큰으로 체결이나 제안을 보내면 `403 INSUFFICIENT_SCOPE` 다.
- 두 사용자 가운데 A 의 체결과 제안은 B 의 어느 응답(검색, 개념 지도 개수, 주변 그래프, 근거 따라가기, 상세, 변경 이력, `/api/v1` 전부)에도 나오지 않는다. ADMIN 인 B 도 같다.
- 열람자가 항목 만들기나 관계 잇기 제안을 승인하면 `403` 이고, 체결과 결정 잇기와 공부 메모 제안은 승인한다. 편집자가 승인한 항목 만들기는 변경 이력에 승인한 사람으로 남는다. 승인이 실패하면 제안은 대기로 남고 오류가 보인다.
- 운영자가 사용자를 지우면 그 사용자의 체결과 제안이 함께 지워진다.
- 「제안」 화면에서 대기 제안의 내용과 까닭을 보고 고쳐 승인하거나 거절하고, 「내 체결」 과 종목 상세에 내 체결이 보이며 다른 사용자의 같은 화면에는 보이지 않는다. 폭 1440px 와 390px 에서 확인한다.
- 다른 사용자의 토큰 목록과 공부 목록은 어느 토큰과 세션으로도 보이지 않는다.
- `/.well-known/oauth-protected-resource/mcp` 와 `/.well-known/oauth-authorization-server` 가 계약의 메타데이터를 돌려주고, 토큰 없이 `POST /mcp` 를 부르면 `401` 과 `WWW-Authenticate`(보호 자원 메타데이터 주소)다.
- 동적 등록이 loopback 의 redirect URI 와, 설정이 허용한 host 의 https redirect URI 만 받는다(기본은 loopback 만). PKCE 가 없거나 S256 이 아닌 인가 요청, 등록하지 않은 redirect URI, 다시 쓴 인가 코드는 거절된다. 코드를 다시 쓰면 그 코드로 만든 연결이 끊긴다.
- 갱신 토큰을 쓰면 새 갱신 토큰이 나오고, 이전 갱신 토큰을 다시 쓰면 `invalid_grant` 이고 그 연결이 끊긴다.
- 「조회만」 연결이나 토큰으로 쓰기 도구를 부르면 도구 오류 `INSUFFICIENT_SCOPE` 다. 연동 토큰으로도 `/mcp` 의 도구를 부른다. A 의 체결은 B 의 어느 MCP 도구 결과에도 나오지 않는다. 연결을 끊으면 그 접근 토큰과 갱신 토큰이 거절된다.
- MCP SDK 클라이언트로 `initialize`, `tools/list`, `tools/call` 이 되고, 실제 Claude Code(`claude mcp add --transport http`)가 로컬 서버에 OAuth 동의를 거쳐 도구 하나를 부른다. Codex 도 지원 방식대로 한 번 붙는다.
- 동의 화면에 앱 이름, 돌아갈 곳, 범위 고르기(기본 「조회와 기록」), 「연결 허용」, 「거절」 이 보이고, 「연동」 화면의 「연결된 앱」 에 그 앱이 나와 「연결 끊기」 로 끊긴다. 폭 1440px 와 390px 에서 확인한다.
- ADMIN 이 웹에서 새 노드 타입을 더해 저장하면 재시작 없이 그 타입의 노드를 만든다. ADMIN 이 아니면 온톨로지를 저장할 수 없다.
- 기존 데이터와 어긋나는 온톨로지 변경은 영향을 확인하지 않으면 저장되지 않고, 예전 버전으로 되돌리면 새 버전이 생긴다.
- 운영 크기의 YAML 에서도 YAML 편집기의 툴바(「저장 전에 확인」, 「초안 버리기」)가 스크롤과 상관없이 보이고, 「저장 전에 확인」 결과가 편집칸 옆(1440px)이나 아래(390px)에 나온다. 오류의 줄 번호를 누르면 그 줄로 간다. 「폼으로 편집」 은 없고 `?view=form` 주소는 YAML 편집기로 열린다.
- 틀린 정의로 올린 온톨로지 변경 제안은 `400` 으로 거절되고, ADMIN 이 아닌 사람의 승인과 기준 버전이 바뀐 뒤의 승인은 거절된다. 승인하면 새 버전과 변경 이력이 생긴다. 「조회만」 연결로 `propose_ontology_change` 를 부르면 `INSUFFICIENT_SCOPE` 다.
- Codex 가 로컬 서버에 붙어 세 가지를 한 번씩 끝낸다. 처음 시작 스킬의 연결 확인과 온톨로지 한눈에 보기, 데이터 추가 제안(`submit_proposals`), 온톨로지 변경 제안(`get_ontology_yaml`, `propose_ontology_change`)이다.
- 「연동」 화면 맨 위에 Claude Code 와 Codex 의 설치 단계와 복사 단추가 있고, 「고급: 개인 비서 연동」 은 접힌 채로 열린다. 폭 1440px 와 390px 에서 확인한다.

## 남은 한계

- Google `sub` 묶음을 푸는 관리 기능이 없다. 사용자가 Google 계정을 바꾸면 운영자가 Neo4j 에서 그 사용자의 `googleSub` 을 직접 지워야 한다.
- 유효 기간의 「미상」 은 값을 비워 두는 것으로만 표현한다. 「확인했으나 모름」 과 「아직 입력하지 않음」 을 가르지 않는다.
- 세션은 API 프로세스 메모리에 있다. API 를 재시작하면 다시 로그인한다.
- 실제 Google 로그인은 배포한 뒤 사람이 확인한다. 자동 테스트와 브라우저 테스트는 가짜 OIDC 공급자를 쓴다.
- 스키마 초기화는 웹 서버가 요청을 받기 전에 끝난다. 초기화가 실패하면 API 가 시작하지 않고 health 도 응답하지 않는다.
- 주장은 주체나 대상 기업의 이름으로 검색되지 않는다. 검색은 저장할 때 만든 검색어로 하고, 주장의 이름은 읽을 때 만들기 때문이다. 주장은 기업 상세나 그래프에서 찾는다.
- 변경 이력의 이름은 지금 이름이다. 노드 이름을 바꾸면 예전 이력의 주체, 대상, 근거 문서 이름도 새 이름으로 보인다. 그때의 이름은 대상 이름(`targetLabel`)만 남는다.
- 링크로 들어와 로그인할 때 보던 주소는 탭 저장소에 둔다. 저장소를 쓸 수 없는 브라우저에서는 로그인한 뒤 첫 화면이 열린다.
- 뒤로가기로 돌아오면 「이웃 확장」 으로 넓힌 그래프와 저장하지 않은 폼 입력은 돌아오지 않는다. 주소에 담지 않는다.
- 인용은 짧게, 출처와 함께 넣는다. 책 본문을 길게 옮기지 않는다. 화면이 길이를 막지는 않으므로(근거 문장 4000자) 사람이 지킨다.
- 개념을 기업에 적용하는 주장(「이 기업은 경제적 해자가 있다」)은 아직 없다.
- 주변 그래프는 최대 2홉이다. 결정에서 변화까지는 4홉이라, 그래프의 「이웃 확장」 으로 한 단계씩 넓혀 따라가거나 근거 따라가기를 연다.
- 근거 따라가기는 한 항목에 여러 길로 닿아도 처음 찾은 길 하나로 보인다. 깊이 6, 60단계를 넘으면 잘린다.
- 근거 상태는 근거 문서와 주장 검토 상태로만 판정한다. 설명에 「원문 대조 대기」 라고 적혀 있어도 근거 문서가 있으면 「근거 있음」 이다.
- 이해 표시에는 이력이 없다. 마지막으로 바꾼 시각만 남는다.
- 연동 토큰에는 만료가 없다. 잃어버리거나 새면 사람이 폐기한다. 발급과 폐기는 변경 이력에 남지 않는다.
- 동적 등록은 누구나 할 수 있어 동의 화면의 앱 이름은 앱이 정한 값이다. 사람은 돌아갈 곳과 자신이 방금 연결을 시작했는지로 판단한다.
- 같은 갱신 토큰을 동시에 두 번 보내는 클라이언트는 연결이 끊겨 다시 로그인해야 한다. 갱신 토큰을 바꾸는 규칙이 이전 토큰의 재사용을 도난으로 보기 때문이다.
- `/mcp` 는 MCP `2025-11-25` 까지 말한다. 세션과 `initialize` 를 없앤 최신 규격(`2026-07-28`)만 말하는 클라이언트는 붙지 못하고, 그때 SDK 를 올린다.
- 플러그인의 MCP 주소는 운영 공개 주소로 정해져 있다. 개발 서버에 붙이려면 `claude mcp add --transport http` 처럼 클라이언트에 직접 더한다.
- `/api/v1` 의 요청 한도는 API 프로세스 메모리에 있어 다시 시작하면 처음부터 센다. 토큰을 가진 에이전트는 주인이 볼 수 있는 모든 지식 데이터와 주인의 체결, 제안을 읽는다.
- 체결 기록에는 변경 이력이 없어 지운 기록을 되살릴 수 없다. 금액은 증권사가 준 값을 그대로 두고 다시 계산하지 않는다.
- 체결의 종목은 저장할 때 찾는다. 체결보다 종목을 나중에 만들면, Hermes 가 그 체결을 다시 보낼 때 이어진다.
- 제안은 만든 때와 승인할 때 온톨로지로 두 번 검사한다. 그 사이 온톨로지가 바뀌거나 가리킨 항목이 보관되면 승인이 실패하고 제안은 대기로 남는다. 승인과 거절은 변경 이력에 남지 않는다.
- 결정한 제안은 90일이 지나면 그 사용자가 다음에 제안을 올릴 때 지워진다. 대기 중인 제안은 200개까지 쌓인다.
- 「쓰는 개념」 관계와 개념 초기 데이터는 운영 온톨로지에 그 관계를 더한 뒤 API 를 다시 시작해야 들어간다([배포](deployment.md) 의 「개념 설명을 운영에 반영할 때」).
- 투자 온톨로지의 연결에는 검토와 근거 문장이 없다. 근거는 연결한 근거 자료뿐이다.
- 관계 문장은 관계 종류의 문장 틀(`sentence`)로 만든다. 틀이 없는 관계는 「{from}이(가) {to}을(를) {표시 이름}」 으로 보여 어색할 수 있다. 운영 온톨로지의 문장 틀과 표시 이름은 이미지 배포로 바뀌지 않아 ADMIN 이 온톨로지 편집기로 넣는다([배포](deployment.md) 의 「저장소 온톨로지의 문구를 운영에 반영할 때」).
- 조사는 이름의 끝소리로 고른다. 영문 약어와 숫자는 읽는 소리 규칙(L, M, N, R 과 0, 1, 3, 6, 7, 8 이 받침)으로 고르므로, 다르게 읽는 이름(예: 영문 낱말)은 조사가 어색할 수 있다.
- 고르기 칸에서 새 항목을 바로 만들 수 없다. 앞 항목이 없으면 먼저 만들거나, 비워 두고 만든 뒤 상세에서 잇는다.
- 개념 지도의 「최근 항목」 은 만든 시각 순서다. 고친 시각은 보지 않는다.
- 초기 데이터에는 친구의 실제 매매 날짜와 밸류에이션이 들어 있고, 저장소는 공개다(사용자 결정 2026-10-24).
- 2026-10-24 에 운영 데이터를 사용자 계정만 남기고 비웠다. 그 전의 기업, 주장, 변경 이력은 남아 있지 않다.
- 동시 수정 때 입력을 지키는 것은 노드 편집 폼뿐이다. 주장 내용 수정 폼은 409 를 받으면 최신 값을 다시 읽고 입력이 사라진다.
- 같은 이름 검사는 검색 결과 앞 100개 안에서만 찾는다. 이름에 같은 글자가 든 항목이 100개를 넘으면 같은 이름을 놓칠 수 있다.
- 종목을 만들며 고른 발행 기업은 따로 요청해 잇는다. 그 요청만 실패하면 발행 기업 없는 종목이 남고, 화면이 안내한다.
- 목록에 없는 예전 국가나 통화 값 가운데 별칭에도 없는 것은 그대로 남는다. 보관된 노드의 예전 값은 복원한 뒤 다음 시작 때 고쳐진다.
- 온톨로지를 바꿔도 기존 데이터는 고치지 않는다. 영향을 확인하고 저장하면 새 정의를 어기는 노드와 관계가 남는다. 그 노드는 어긴 칸을 고칠 때 새 정의를 따른다.
- 저장소 YAML 의 편집할 수 있는 부분(타입, 관계 종류, 주장 종류)은 첫 버전을 만든 뒤로 쓰지 않는다. 코드 변경이 새 타입을 필요로 하면 배포한 뒤 ADMIN 이 웹에서 더한다.
- 온톨로지 키(타입, 속성, 관계 종류, 주장 종류, enum 값의 이름)는 바꿀 수 없다. 빼고 새로 더하면 기존 데이터는 옛 키로 남는다.
- 다른 관리자가 온톨로지를 바꿔도 열려 있는 화면은 저절로 다시 읽지 않는다. 머리글의 안내에서 「다시 읽기」 를 눌러야 바뀐 타입과 칸이 보인다.
- 가이드의 연습 주장은 보관되기 전까지 다른 편집자의 검토 대기에 보일 수 있다. 연습 항목을 만들고 보관한 일은 변경 이력에 남는다.
- 창(Dialog, Sheet)이 열려 있어도 뒤 화면이 스크롤된다. 스크롤 잠금이 넣는 `<style>` 을 CSP 가 막기 때문이다. 근거는 [코드 구조](code-architecture.md) 의 「보안 기본값」 이다.
- 만들기 창이 열린 동안에는 창 밖의 요소가 화면 낭독기에서 숨겨진다(Radix 모달 창의 동작). 그래서 따라하기 말풍선은 마우스로는 누를 수 있지만 키보드 초점과 화면 낭독기는 닿지 않는다. 창을 닫으면 다시 닿는다.

## FOS 연동 경계

| 영역 | 책임 |
| --- | --- |
| 가치투자 온톨로지(이 저장소) | 금융 지식, 근거, 시점, revision, 검색 |
| FOS Control Plane | 사용자, 계좌 권한, 승인, 전략 정책, 주문, 체결 |
| Toss 커넥터(`fos-assistant`) | 공식 API 인증, 조회, 실행 |
| 워크벤치 커넥터(`fos-assistant`) | 사용자가 넣은 연동 토큰으로 `/api/v1` 을 불러 Hermes 에 조회 도구와 체결 기록, 제안 도구를 준다. 플러그인 표준과 원격 MCP 를 받으면 이 저장소의 플러그인과 `/mcp` 로 옮긴다 |
| 플러그인(이 저장소의 `plugin/`) | Claude Code, Codex 에 원격 MCP 연결 설정과 쓰는 법(스킬)을 준다. 도구는 서버의 `/mcp` 에 있다 |

공유 지식그래프의 편집 권한과 개인 증권계좌의 실행 권한은 따로 둔다.
개인 계좌 키, 잔고, 주문 내역은 이 그래프에 넣지 않는다. 온톨로지에도 그런 타입이 없다. 체결 기록은 지식 그래프 밖에 주인만 보는 기록으로 둔다([ADR-013](adr/013-owner-trades-and-agent-proposals.md)).
후속 도구가 쓸 응답 필드는 [API 계약](api-contract.md)의 「후속 도구가 쓸 필드」 절에 있다.
에이전트가 부르는 조회와 쓰기 계약은 [API 계약](api-contract.md)의 「에이전트 API(`/api/v1`)」 절이다.
관련 후속 과제는 https://github.com/jon890/fos-assistant/issues/593 이다.

## 다음 GraphRAG 마일스톤

이번 마일스톤에서는 구현하지 않는다. 다음 단계의 범위만 정의한다.

| 단계 | 하는 일 | 이번 구조에서 이어 쓰는 것 |
| --- | --- | --- |
| 문서 분할 | 등록된 Document 의 원문을 사람이 올리거나 허용된 출처에서 받아 문단 단위 `:Chunk` 로 나눈다. Chunk 는 Document 와 `PART_OF` 로 잇고 위치(시작, 끝 오프셋)를 가진다 | Document 의 `id`, `url`, `publishedAt`, `collectedAt` |
| 개체 연결 | Chunk 에 나온 기업명과 종목 코드를 기존 Company, Security 의 `id` 에 연결한다. 확신이 낮은 연결은 후보로만 남긴다 | `security_listing_unique` 와 `searchText` |
| 검토 대기 Claim 추출 | 모델이 Chunk 에서 온톨로지 predicate 에 맞는 Claim 을 뽑아 `authoringMethod = AI`, `reviewStatus = DRAFT`, `extractionConfidence` 를 채워 저장한다. 사람이 검토 대기 화면에서 승인한다 | Claim 스키마, 검토 API, 온톨로지 검증기 |
| 근거 기반 검색 | 질문을 받아 Chunk 임베딩 검색과 그래프 이웃 탐색을 합친다. 기본은 `REVIEWED` Claim 만 쓴다 | 주변 그래프 API 의 한도 정책 |
| 출처를 포함한 답변 생성 | 답변마다 사용한 Claim 의 `id`, `revision`, Document `url`, 근거 문장을 붙인다. 근거가 없으면 답하지 않는다 | `get_evidence` 가 쓸 `ClaimView` |

이 단계에서 Ollama 와 임베딩 모델을 Compose 에 넣을지는 홈서버 자원을 확인한 뒤 정한다.
