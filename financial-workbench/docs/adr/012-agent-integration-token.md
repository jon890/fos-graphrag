## ADR-012: 에이전트는 개인 연동 토큰으로 Bearer 전용 `/api/v1` 조회 API 를 부른다

- **status**: `accepted`
- **결정**: 사용자가 웹의 「연동 토큰」 화면에서 개인 연동 토큰을 발급하고, 외부 에이전트(fos-assistant 의 Hermes)는 그 토큰을 `Authorization: Bearer` 헤더에 담아 `/api/v1/**` 를 부른다. `/api/v1/**` 는 Bearer 토큰만 받고 세션 쿠키와 CSRF 를 쓰지 않는다. 기존 `/api/**` 는 세션과 CSRF 만 받고 Bearer 토큰을 받지 않는다. 토큰은 발급한 사용자로 인증되고 그 사용자의 역할을 따르지만, `/api/v1` 에는 조회 경로만 있다. 토큰에는 만료가 없고 사용자가 폐기한다. 서버는 원문의 SHA-256 해시만 저장한다. 연결 방향은 Hermes → 워크벤치 공개 주소이고, 워크벤치를 Hermes 내부망에 붙이지 않는다.
- **맥락**: 사용자는 Hermes 에 워크벤치 그래프를 조회하는 도구를 붙여, 이미 붙어 있는 토스증권 커넥터와 같은 profile 에서 함께 쓰려 한다(사용자 결정 2026-10-25). 워크벤치는 Google 로그인 세션과 쿠키 CSRF 로만 인증한다([ADR-006](006-google-oidc-allowlist-roles.md), [ADR-004](superseded/004-session-csrf-same-origin.md)). 서버에서 도는 에이전트는 브라우저 로그인을 할 수 없다. 가계부는 같은 요구를 개인 연동 토큰으로 풀었다(가계부 백엔드 ADR-B18, 홈서버 ADR-029). 두 사람이 쓰는 도구이고 워크벤치의 공개 주소가 이미 모든 경로를 프록시한다. 이번 단계는 조회만 하고, 체결 기록 쓰기와 본인만 열람하는 권한은 다음 단계다.
- **ADR-004 와의 관계**: 세션, 쿠키 CSRF, 같은 origin 제공은 `/api/**` 에 그대로다. `/api/v1/**` 는 브라우저가 부르지 않는 경로라 CSRF 가 막으려는 공격(브라우저가 쿠키를 자동으로 싣는 요청)이 성립하지 않는다. 그래서 그 경로에서는 쿠키를 아예 읽지 않고 CSRF 를 끈다. 한 요청이 두 인증을 섞어 쓰는 일이 없도록 경로로 가른다.
- **대안 기각**:

  | 대안 | 기각 이유 |
  | --- | --- |
  | 세션 쿠키를 에이전트에 넘긴다 | 세션은 API 프로세스 메모리에 있어 재배포 때마다 끊기고, 8시간 유휴 만료가 있다. 쿠키 하나로 사용자 관리와 쓰기까지 모든 `/api/**` 가 열린다 |
  | OAuth 클라이언트 등록(client credentials, device flow) | 인가 서버, 동의 화면, refresh token 저장을 새로 만들어야 한다. 두 사람이 쓰는 도구에 비해 크고, 사용자 한 명을 대신한다는 점은 개인 토큰과 같다 |
  | Hermes 내부망을 공유한다 | 홈서버 ADR-039 가 기각한 위험이다. 워크벤치가 Hermes 의 다른 컨테이너와 같은 망에 놓이고, 내부망이라는 이유로 인증을 약하게 둘 유혹이 생긴다 |
  | 워크벤치가 Hermes API 를 부른다 | 방향이 반대라 워크벤치가 Hermes 의 자격증명을 들고 있어야 한다. 에이전트가 필요할 때 조회하는 흐름과 맞지 않는다 |
  | 토큰으로 기존 `/api/**` 를 그대로 부르게 한다 | 화면용 응답(`NodeView` 의 모든 시스템 속성, 사용자 이메일)이 에이전트 문맥을 채우고, 화면 계약을 바꿀 때마다 커넥터가 깨진다. 쓰기와 사용자 관리 경로를 경로별 허용 목록으로 막아야 한다 |
  | 토큰에 90일 만료를 둔다 | 만료될 때마다 Hermes profile 의 토큰을 바꿔야 연동이 이어지고, 만료를 놓치면 에이전트가 조용히 실패한다. 마지막 사용 시각과 폐기로 대신한다(가계부 ADR-B18 과 같은 판단) |
  | 해시를 bcrypt 로 한다 | 원문이 무작위 32바이트라 느린 해시가 막을 추측 공격이 없다. 요청마다 찾아야 해 SHA-256 유일 제약으로 바로 찾는다 |
  | 토큰마다 조회 범위(scope)를 고르게 한다 | `/api/v1` 이 조회뿐이라 고를 것이 없다. 쓰기 경로를 더할 때 다시 정한다 |

- **결과**:
  - 얻는 것: Hermes 가 사용자 권한 안에서 그래프를 조회한다. 토큰이 새도 쓰기, 사용자 관리, 토큰 발급에는 닿지 못한다. 에이전트용 응답(v1 DTO)이 화면 계약과 따로 움직여, 화면을 고쳐도 커넥터가 깨지지 않는다. 비활성화하거나 허용 목록에서 뺀 사용자의 토큰은 다음 요청부터 막힌다.
  - 감당할 것: `/api/v1` 계약은 다른 저장소의 커넥터가 따르는 공개 계약이다. 필드를 빼거나 뜻을 바꾸면 `/api/v2` 를 만들고, 더하기만 v1 에서 한다. 서버는 v1 DTO 와 화면 DTO 를 따로 유지한다. 요청 한도(토큰마다 분당 60회)는 API 프로세스 메모리에 있어 재시작하면 초기화되고, 인스턴스를 늘리면 인스턴스마다 따로 센다. 토큰 원문은 발급 응답에만 실리고 잃어버리면 폐기하고 새로 발급한다. 사용자당 5개 상한은 사용자 노드를 잠근 뒤 센다. 폐기는 다음 요청부터 적용되고 이미 인증을 통과한 요청은 끝까지 처리된다. 마지막 사용 시각은 1분에 한 번만 쓰고, 기록이 실패해도 요청은 처리한다. 토큰을 가진 에이전트는 그 사용자가 볼 수 있는 모든 지식 데이터와 그 사용자의 이해 표시를 읽는다. 투자 결정과 밸류에이션의 열람 제한은 아직 없다.
- **적용 범위**: 저장 모델은 [데이터 스키마](../data-schema.md) 의 「연동 토큰」, 계약은 [API 계약](../api-contract.md) 의 「연동 토큰」 과 「에이전트 API(`/api/v1`)」, 화면과 인증 흐름은 [흐름](../flow.md) 의 「연동 토큰」 과 「에이전트 조회」 가 소유한다.
