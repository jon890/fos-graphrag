## ADR-010: 첫 화면을 개념 지도로 두고, 탭 셋과 더보기 메뉴, 읽기 우선 상세, 전역 「＋ 추가」 로 화면 구조를 바꾼다

- **status**: `accepted`
- **결정**: 상단 탭을 「개념 지도」(`/map`), 「작업 공간」(`/workspace`), 「목록」(`/list`) 셋으로 줄이고, 변경 이력, 온톨로지 상세, 검토 대기, 사용자는 오른쪽 위 「더보기」 메뉴 하나에 역할별로 둔다. 첫 화면(`/`)은 온톨로지의 타입과 관계를 그린 개념 지도다. 작업 공간의 상세 칸은 읽기 카드가 기본이고 「편집」 을 눌러야 편집 폼이 열린다. 항목 만들기는 모든 화면의 같은 자리에 있는 「＋ 추가」 하나에서 시작한다. 추가 메뉴와 검색 칩의 타입 순서는 온톨로지를 바꾸지 않고 관계 방향으로 계산한다.
- **맥락**: 운영 화면을 본 사용자가 일반 사용자에게 작업 공간이 복잡하다고 했다(2026-10-24). 탭이 여섯 개이고, 검색 칸에 필터가 모두 펼쳐져 있고, 상세 칸이 처음부터 편집 폼과 보관 사유 입력칸이며, 만들기 버튼은 검색 결과 아래에 있어 찾기 어려웠다. 온톨로지 탭은 속성 표와 관계 키 이름이라 개발자용이었다. 사용자는 온톨로지 개념을 첫 화면에서 그림으로 보고, ＋ 모양의 추가 버튼을 위쪽 눈에 띄는 자리에서 쓰기를 원했다.
- **대안 기각**:
  - 지금 구조 유지와 문구만 다듬기: 바꾸는 코드가 적지만 탭 여섯 개와 펼쳐진 필터, 편집 폼 상세는 그대로라 사용자가 말한 복잡함이 남는다.
  - 온톨로지 YAML 에 타입 묶음(`group`)이나 순서 필드를 더해 메뉴를 묶기: 원하는 순서를 그대로 적을 수 있지만, 운영 온톨로지는 DB 의 버전이라 저장소 YAML 의 새 필드가 운영에 닿지 않는다([ADR-008](008-ontology-versions-in-db.md)). 서버 검증기와 편집기도 함께 고쳐야 한다. 관계 방향으로 계산한 순서는 타입과 관계가 늘어도 그대로 따라간다.
  - 고르기 칸에서 바로 새 항목 만들기: 변화에서 결정까지 이어 만들 때 화면을 떠나지 않지만, 폼 안에 폼이 열려 실패와 취소 갈래가 두 겹이 된다. 사용자가 이번에는 넣지 않기로 했다.
- **결과**:
  - 얻는 것: 처음 들어온 사람이 무엇을 담는 도구인지 그림으로 본다. 탭 셋과 ＋ 추가만 보면 일상 작업을 할 수 있다. 상세는 관계를 문장으로 읽는다. 타입이나 관계가 늘면 지도, 추가 메뉴, 검색 칩이 함께 늘어난다.
  - 감당할 것: 관계 문장을 자연스럽게 보이려고 관계 종류에 선택 필드 `sentence`(`{from}`, `{to}` 를 담는 문장 틀)를 더했다. 온톨로지 계약과 서버 검증기, 폼과 YAML 편집기가 함께 바뀐다. 틀이 없는 관계는 「{from}이(가) {to}을(를) {label}」 로 보여 어색할 수 있고, 운영 온톨로지에는 배포 뒤 관리자가 틀을 넣어야 한다. 관계 표시 이름 하나로 양쪽 방향 문장을 만드는 안은 「FLNC가 FLNC 첫 매수를 받습니다」 처럼 어색해 버렸다. 더보기 메뉴로 옮긴 화면은 한 번 더 눌러야 열린다. 고르기 칸에서 바로 만들 수 없어 앞 항목이 없으면 먼저 그것을 만들어야 한다.
- **[ADR-007](007-routes-in-url.md) 과의 관계**: 주소 규칙은 그대로다. 화면 경로와 query 이름을 바꾸지 않고 `/map` 하나를 더한다. 더보기 메뉴로 옮긴 화면도 같은 경로로 열리므로 이미 보낸 링크가 그대로 열린다. 바뀌는 것은 `/` 가 바꿔 여는 곳(`/workspace` 에서 `/map`)뿐이다.
- **적용 범위**: 경로와 화면 흐름은 [흐름](../flow.md) 의 「주소와 뒤로가기」, 「개념 지도」, 「노드 만들기」, 「작업 공간」 이, 개수 API 는 [API 계약](../api-contract.md) 의 「노드」 가, 웹 모듈 배치는 [코드 구조](../code-architecture.md) 의 「웹 구조」 가 소유한다.
